## Architecture

**Stack:** Laravel 11 (PHP 8.2 in production/Railway via `nixpacks.toml`; `composer.json`'s own floor is `^8.2` — see the openspout correction under "Excel import (Phase 7)" below for how this was confirmed) · Blade templates (legacy) + Inertia/React (multi-company Platform, in progress) · Supabase (PostgreSQL via REST, plus a direct `pgsql` Postgres connection for Platform migrations/RLS) · OpenAI API · Telegram Bot API

There are now two parallel systems in this codebase, both live in the same production Supabase project (`eavmrurxxdxbufkkzlup`):

- **The legacy single-tenant app** (this whole file, historically) — Blade views, session-based auth against an `employees` table, `EXECUTIVE/MANAGER/VP/SLT` roles.
- **The multi-company Platform** (see below) — Inertia+React, Supabase Auth, Postgres RLS. This is the active development target; the legacy app's `employees` table doesn't exist in production anymore (confirmed live), so its controllers/routes are effectively dead code until/unless a real migration path is built. `/` and `/login` already redirect to `/platform/login` for this reason.

### Database — Supabase REST only, never Eloquent

All database access goes through `app/Services/SupabaseService.php` using Laravel's `Http::` facade. There are no Eloquent models used in practice — every DB call uses:

```php
$supabase->get('table', ['column' => 'eq.value', 'select' => '*']);
$supabase->insert('table', $data);
$supabase->patch('table', $filters, $data);
$supabase->delete('table', $filters);
```

The one exception is the `sessions` table which is a standard Laravel SQLite-backed session (migrations exist for it).

### Session Structure

After login and company selection, the session contains:

```
employee_uuid            — primary identifier used in all DB queries
employee                 — array: id, role, short_name, department, department_code, company_code, manager_id, vp_id, reports_to_id
selected_department_code — set when SLT switches department view
available_dashboards     — list of company/employee combos this user can access
```

The `kpi.auth` middleware (`app/Http/Middleware/KpiAuth.php`) guards all protected routes by checking `employee_uuid`.

### Role Hierarchy

`EXECUTIVE → MANAGER → VP → SLT`

All approval routing and permission checks are based on this chain. `ApprovalHierarchyService` resolves the approver for any given employee. Sensitive KPI actions (edit, target change, delete) go through `ApprovalController` / `ApprovalActionService`.

### AI — ANIRA

All OpenAI calls live in `app/Services/AiService.php` using `Http::` (same pattern as Supabase). Model set in `protected string $model`.

- `chat(messages, employee)` — powers ANIRA floating chat widget; acts as KPI coach, not a generator; system prompt includes full KPI system knowledge, role hierarchy, linkages, and activity log context
- `scoreKpiDescription(title, description, baseTarget, stretchTarget, unit, weightage, category, subCategory, quarterTargets)` — scores a complete KPI out of 10 using a calibrated 5-dimension rubric (title, description, target ambition, quarterly distribution, overall coherence)
- `suggestKpiDescription(title, department, role)` — generates a KPI description
- `suggestQuarterlyTargets(title, annualTarget, unit)` — suggests Q1–Q4 split

The ANIRA chat widget (`resources/views/partials/ai-chat-widget.blade.php`) is included via `partials/sidebar.blade.php` and appears on every authenticated page. The ANIRA score card sits in the KPI create form's summary sidebar above the Submit button.

The Platform has its own, separate ANIRA at `/platform/anira` (`AniraController`, `AiService::chatForPlatform()`) — see "ANIRA tenant-aware permission resolution" under the Multi-Company Platform section for how it works and why it's a different code path entirely, not a shared one.

### KPI Scoring Formula

```
Overall Score = Σ(achievement% × weightage%) / Σ(weightage%)
```

Per-KPI achievement (`KpiController::calculateAchievement()`):
- `actual < base` → `(actual / base) × 100`
- `actual > base` with stretch → `100 + ((actual - base) / (stretch - base)) × 100`, capped at 200%
- No stretch set → capped at 100%

## Multi-Company Platform (new architecture, in progress)

A parallel rebuild adding real multi-tenancy: one Richworks "Center" that can see every company, each company fully isolated from every other. Confirmed live in production as of 2026-08-14 — schema, RLS, and helper functions all verified directly against the database, not just inferred from code.

### CORE PLATFORM RULE — tenant isolation

**This is the one rule in this codebase that is not negotiable. Read it before writing any Platform code, migration, or query.**

The tenancy hierarchy is:

```
Performix Platform → Company (tenant) → Users → KPI → Targets/Results
```

1. **Every company-owned table carries its own `company_id`.** Not a joinable path to one — an actual column, `NOT NULL`, foreign-keyed to `companies`, and indexed. If you cannot answer "which tenant owns this row?" by looking at the row itself, the table is wrong.
2. **PostgreSQL RLS is the final authority on access.** Every company-owned table has RLS enabled and policies shaped `auth_is_richworks_super_admin() OR <company_id-scoped condition>`, routed through the `auth_*()` helpers.
3. **`WHERE company_id = ?` in application code is a performance optimisation, never a security control.** Keep writing those filters — they keep queries fast and intent readable — but deleting one must never widen what a caller can see. If it would, the RLS policy is the bug, not the missing filter.
4. **`company_id` is immutable once set**, enforced by `BEFORE UPDATE` triggers (not `WITH CHECK` subqueries, which recurse — see `2026_08_14_080000`). Where it's derivable from a parent row it is *derived server-side*, never taken from the client.
5. **Never use `SupabaseService` (service_role) for Platform reads or writes.** It bypasses RLS entirely. Use `SupabaseUserService`, which carries the caller's own token. The three existing service_role uses (`CompanyController::storeAdmin`, `DepartmentController::storeUser`, `UserCreationController::store`) are narrow, deliberate exceptions: reading back a `users` row that was just created and which the caller provably cannot see yet under RLS. **This is enforced, not just documented:** `SupabaseService::TENANT_OWNED_TABLES` makes every tenant-owned table (`company_users`, `department_users`, `departments`, `kpi_categories`, `kpis`, `kpi_submissions`, `roles`, `notifications`, `kpi_access_grants`, `platform_admin_assignments`, `import_batches`, `audit_logs`, `reports`) throw on any read or write through that client — see "ANIRA/Telegram data-leak audit" below for why.

**Tables exempt from rule 1, and why** — exempt from `company_id`, never from RLS: `companies` (is the tenant), `users` (global identity, scoped through `company_users`), `kpi_templates`/`kpi_template_items` (shared Center-curated library, copy-on-apply so no tenant data lives in them), `admin_action_logs` (Center-only cross-company audit trail; it has `target_company_id`, which is a different thing). Adding `company_id` to any of these would be cargo-culting the rule, not applying it.

**Checking conformance:** `database/rls-tests/tenant_isolation_rule_check.sql` audits the live schema against this rule — missing `company_id`, nullable/unconstrained tenant keys, tables without RLS or without policies, SELECT policies that never reference the tenant, and tenant keys with no immutability trigger. Read-only, safe against production. Sections 1–6 must return zero rows; section 7 reports known open items (no DELETE policies anywhere; no `FORCE ROW LEVEL SECURITY`, which would also subject the `SECURITY DEFINER` helpers to the policies that call them — a recursion risk, not a free win). Behaviour, as opposed to shape, is covered by `tenant_isolation.sql`, which is still unrun.

**Conformance confirmed clean against production, 2026-08-17** (`psql` isn't installed on this dev machine, so the script's literal queries were run via `php artisan tinker` instead — same SQL, same result). Sections 1–6 all returned zero rows after two fixes made during that run:

- **`company_users.company_id` had no immutability trigger** — a real, pre-existing gap (not a regression from this session's own work), traced to `2026_08_12_000000_create_platform_foundation_schema.php`'s original `company_users_update` policy, which only ever validated the new row's company membership, never compared it against the old row. Unlike the five tables `2026_08_14_080000` already covers, this one was never touched by any prior migration. Fixed in `2026_08_17_120000_freeze_company_users_company_id.php` by attaching the same pre-existing `prevent_company_id_change()` trigger everything else uses — one trigger attachment, no new logic. Without it, anyone administering two companies (an unremarkable schema state — a multi-company Platform Admin, for instance) could have UPDATEd a `company_users` row to move a user's membership from one company to another, which is exactly the boundary-crossing rule 4 exists to prevent.
- The check script itself had a blind spot: sections 2 and 6 queried `information_schema.columns` directly, which — unlike section 1's `pg_tables` — doesn't distinguish base tables from views, so `company_kpi_summary` (a `security_invoker` view that happens to expose a `company_id` column) was flagged as missing a FK/NOT NULL/trigger it structurally cannot have. Fixed by adding an explicit `pg_class.relkind = 'r'` check to both sections.

### CONFIGURATION TIERING RULE — platform-level vs. company-level

A sibling to the tenant isolation rule above, but about *configuration* rather than *data*: every configuration surface belongs at exactly one tier, and mixing them is how one company's setup starts leaking into or overriding another's. The scalability property this protects is literally "Andalusia can configure its KPIs differently from VFive without affecting VFive" — which, for everything that's actually built, is already true and already verified (see the tenant isolation conformance record above). This section exists so that as the remaining pieces get built, they land on the correct tier the first time instead of needing a later migration to fix it.

**Platform-level** (no `company_id`, Center/Super-Admin-only — the same shape as the tenant-isolation rule's own exemption list):

| Area | Status |
|---|---|
| Authentication | Inherently platform-level already — Supabase Auth is one global identity provider, not per-company; there was never anything to separate here. |
| Global KPI templates | **Built.** `kpi_templates`/`kpi_template_items` — no `company_id`, Super-Admin-only writes (`KpiTemplateController`), copy-on-apply into a company's own `kpis` (Phase 9). |
| Audit engine | **Built.** `admin_action_logs` — no `company_id` (has `target_company_id`, which is a different thing: a foreign key to the company an action was *about*, not an owner), RLS restricted to `auth_is_richworks_super_admin()`. No separate "audit configuration" (retention policy, what gets logged) exists — logging behavior is hardcoded in `LogsAdminActions`. |
| AI provider | **Missing.** `AiService::$model` and `OPENAI_API_KEY` are hardcoded/env-only — no DB row, no admin UI, nothing to separate yet because nothing is configurable at all. |
| ANIRA engine | **Partially built.** The Platform's ANIRA chat (`AniraController`, `AiService::chatForPlatform()`) now exists and is tenant-aware — see below. There's still no *configurable* engine settings (model choice, retry/timeout policy) — `$model` and prompt structure are hardcoded, same as the legacy `AiService`. |
| Telegram infrastructure | **Missing** for the Platform. Env vars (`TELEGRAM_BOT_TOKEN` etc.) configure the one legacy bot; there is no concept of Platform-level Telegram infrastructure because no Platform Telegram integration exists (the only Telegram code is the legacy one `SupabaseService::TENANT_OWNED_TABLES` now blocks from touching Platform data). |
| Subscription/billing | **Missing entirely.** Zero references anywhere in the codebase — no table, column, model, or controller. Not a misplaced feature; a nonexistent one. |
| System settings | **Missing.** No generic settings table exists at either tier. Branding (`display_name`/`primary_color`/`secondary_color`) was deliberately added as plain columns on `companies` instead of a settings table for exactly this reason (see `2026_08_14_030000`'s own docblock) — a pattern worth repeating rather than reaching for a generic key-value table prematurely. |

**Company-level** (carries `company_id`, or is reachable only via a `company_id`-scoped parent — RLS-scoped per the tenant isolation rule):

| Area | Status |
|---|---|
| Employees | **Built.** `company_users` (has `company_id`) / `department_users` (scoped via `department_id → departments.company_id`). |
| Departments | **Built.** `departments` — has `company_id`. |
| Roles | **Built.** `roles` (per-department configurable job-level labels) — scoped via `department_id → departments.company_id`. |
| KPI templates/configuration | **Built.** `kpis`/`kpi_categories` — both have `company_id`. Per-KPI visibility grants (`kpi_access_grants`, Phase 14) also carry `company_id`. |
| Targets | **Built.** `kpis.target` — one current target per KPI, not per-period (the per-employee/per-period `kpi_targets` split from the original spec was deliberately not built — see Phase 2's own note). |
| KPI results | **Built.** `kpi_submissions` — has `company_id`. |
| ANIRA preferences | **Missing.** No columns on `companies`, no separate table — ANIRA itself works per-company now (it just answers with whatever that company's RLS-authorized data is), but there's no way for a company to customize *how* it behaves (tone, enable/disable, model choice). |
| Telegram settings | **Missing.** Same reasoning — no Platform Telegram feature exists yet to configure per company. |
| Reporting structure | **Missing.** No manager/reports-to relationship exists anywhere in the schema (`company_users`, `department_users`, `departments` all lack it) — confirmed while building the onboarding wizard's "Configure reporting hierarchy" placeholder (Phase 15). |

**Why nothing was built for the 8 missing items in this pass:** every one of them is a genuinely new feature, not a misplaced existing one — there is no code today that reads an AI-provider setting, a subscription plan, a reporting-hierarchy edge, or a Telegram-per-company setting, because none of those features exist. Creating settings tables/columns for them now, with nothing anywhere reading or writing them, would be exactly the kind of unwired scaffolding this codebase deliberately avoids elsewhere (e.g. the original honest "Import isn't built yet" placeholder before Phase 7, or the three onboarding-wizard steps left as `builtYet: false` rather than faked). When any of these 8 gets built for real, this table is where its tier is already decided — Subscription/billing and System settings are platform-level; ANIRA preferences, Telegram settings, and Reporting structure are company-level; AI provider and ANIRA engine config could reasonably be either (a platform-wide default the Center sets, optionally overridden per company) and that's a real product decision to make at build time, not before.

### Why this exists, and how it differs from the legacy app above

The legacy app has no real tenant isolation mechanism beyond `company_code` filters an engineer has to remember to add in every controller. The Platform replaces that with **Supabase Auth + Postgres Row-Level Security**: every non-privileged request carries the caller's own Supabase Auth access token (never `service_role`), so `auth.uid()` resolves to a real person inside Postgres and RLS policies — not application code — decide what's visible. A bug in a controller, a raw SQL script, or someone editing rows directly in the Supabase table editor still can't cross a company boundary.

### Role hierarchy

Two independent axes (since Phase 14, `2026_08_17_110000_separate_platform_and_company_roles`, applied 2026-08-17):

```
PLATFORM TIER (users.role)          scope
-----------------------------------  --------------------------------------
richworks_super_admin                every company, unconditionally
platform_admin                       ONLY companies explicitly assigned via
                                      platform_admin_assignments
member                               no platform-wide powers at all

COMPANY TIER (company_users.role)   scope within that one company
-----------------------------------  --------------------------------------
company_admin                        full administration of own company
slt                                  company-wide KPI visibility, read-only,
                                      minus anything marked `restricted`
executive                            own department's permitted KPI data
employee                             own submissions + own department's
                                      permitted KPI data
```

A Platform Admin is deliberately not "a weaker Super Admin" — it has no implicit reach at all; every company it can touch is an explicit `platform_admin_assignments` row, granted/revoked only by a Super Admin (`PlatformAdminController`, `/platform/admins`). `richworks_super_admin` keeps its name (not renamed to `platform_super_admin`) because it's the already-live stored value and `auth_is_richworks_super_admin()` is called by ~30 policies — a half-finished rename of an authorization predicate is exactly the kind of change that fails open. `department_admin`/`department_user` *were* renamed, to `executive`/`employee`, because those are matched as plain strings in a countable number of places (all updated in the same migration) — leaving two naming systems for the same concept is how authorization bugs get written. Each department can also define its own configurable job-level labels via the `roles` table (e.g. "Staff", "Lead") — cosmetic ordering only, not a permission tier.

**Per-KPI visibility.** `kpis.visibility` sets a KPI's default reach: `'company'` (any member may read it — the default, and what every pre-existing KPI was backfilled to, so this change narrowed nobody's access), `'department'` (only the departments that submit against it, plus admins/SLT), or `'restricted'` (nobody by default). `kpi_access_grants` widens that for one specific user or department — exactly one grantee per row (`num_nonnulls(user_id, department_id) = 1`), tenant-checked by `trg_validate_kpi_grant_tenancy` so a grant can never cross a company boundary. The single predicate deciding "can this caller see this KPI" is `auth_can_view_kpi(kpi_id)`, called by both `kpis_select` and `kpi_submissions_select` so the two can't drift apart. Managed from each company's KPI page (`KpiController::storeGrant()`/`destroyGrant()`, `/platform/companies/{company}/kpis/{kpi}/grants`).

Creates disposable fixtures, simulates `auth.uid()` per Supabase's own convention (`request.jwt.claims` + `SET LOCAL ROLE authenticated`), and rolls back unconditionally at the end. **Company activation/suspension (Phase 5):** `CompanyController::activate()/suspend()/reactivate()/updateBranding()` — the first two Center-management pieces the Companies index page was still missing. Suspension is enforced at the RLS layer, not just a status label: `2026_08_14_060000_enforce_company_suspension_in_rls.php` tightens `auth_company_ids()`, `auth_role_in_company()`, and `auth_department_ids()` (the three helper functions nearly every policy routes through) to exclude `suspended`/`inactive` companies — so a suspended company's own users lose read/write access on their very next request, not just in the UI. Known cosmetic gap: `PlatformAuth`'s `company_memberships` list doesn't route through those functions (it's gated by `company_users_select`'s own-row branch instead), so a suspended company's admin still sees a dead nav link rather than it disappearing — the actual data boundary holds regardless. Also added: a Center "company switcher" — the Dashboard's and Companies index's company lists now link directly into each company's Departments/KPIs pages, which a pure Super Admin (no `company_users` row of their own) previously had no way to reach at all.

**Tenant isolation as a structural rule (Phase 13, applied to production 2026-08-17).** `2026_08_17_100000_enforce_tenant_isolation_rule.php` closes the two places the schema didn't actually satisfy the Core Platform Rule above. `department_users` and `roles` are unambiguously company-owned but carried no `company_id` — their policies reached the tenant boundary by joining through `departments` on every check. That worked, but it made the boundary an emergent property of a join instead of a column, and it meant those were the only two tables where "which tenant owns this row?" couldn't be answered from the row. Both now carry `company_id` (backfilled, `NOT NULL`, FK'd, indexed), and their policies scope on it via `auth_company_ids()`/`auth_role_in_company()` — which also means both finally pick up the Phase 5 company-suspension enforcement their hand-rolled joins partly sidestepped. Access semantics are otherwise unchanged, deliberately: this is a rewrite of *how* the boundary is expressed, not *where* it sits.

`company_id` on those two tables is **derived, never trusted** — a `BEFORE INSERT OR UPDATE` trigger (`derive_company_id_from_department()`) overwrites whatever the client sent with the parent department's real company, so a mismatched value isn't rejected, it's unrepresentable. It's then frozen by the existing `prevent_company_id_change()`; trigger names matter here, since Postgres fires `BEFORE` triggers alphabetically and `trg_derive_company_id` must run before `trg_prevent_company_id_change`. Also added `prevent_roles_reassignment()` — `department_users.department_id` was already frozen by `2026_08_14_080000` but `roles.department_id` wasn't, so a role could be moved to another department and (once it carries `company_id`) transitively across companies. And `notifications`, which had `company_id` all along but whose policies referenced only `user_id`, is now tenant-scoped too: strictly narrower than the boundary so it never leaked, but it was the one table where the column existed and went unused, which is also why it never picked up suspension enforcement.

`database/rls-tests/tenant_isolation_rule_check.sql` is the companion — a read-only schema audit that fails loudly if any of this drifts (missing `company_id`, nullable/unconstrained tenant key, RLS off, RLS on with no policies, a SELECT policy that never mentions the tenant, a tenant key with no immutability trigger). Safe against production, unlike its behavioural sibling `tenant_isolation.sql`.

### Real end-to-end verification pass, 6 production bugs found and fixed (2026-08-17, same session)

User asked whether all 7 requests were "end to end action functional technically" and to "make it function" — not just structurally correct, but actually exercised. Everything up to this point had been verified via `Http::fake()`-based tests (which prove the CODE'S logic is right) and read-only production schema checks (which prove the SCHEMA'S shape is right) — neither can catch a bug in how the two actually talk to each other. So this pass bootstrapped a real, temporary Richworks Super Admin (`platform:bootstrap-super-admin`), created a real disposable company, and drove every flow through genuine HTTP requests with real cookies/CSRF against a local `php artisan serve`, backed by the real production Supabase project — company creation, Company Admin invite, department/role/KPI creation, KPI submission, company lifecycle transitions, ANIRA chat, and Telegram linking, each as the actual role that uses it day to day (Super Admin, Company Admin, Employee), not as whichever role happened to be convenient.

This surfaced **six real, previously-undetected production bugs** that no amount of mocked testing could have caught, because every one of them is a mismatch between this codebase's assumptions and Supabase/Postgres's actual behavior — not a logic error mocked tests would have exercised the same way either:

1. **`PlatformAuth` resolved the wrong user's identity.** `$supabase->first('users', ['select' => '...'])` with no filter relied on RLS alone to narrow the result to "just me" — but RLS grants VISIBILITY (every row in `users` for a Super Admin; every user in your own company for a Company Admin), not IDENTITY. With no filter and no explicit order, PostgREST returns an arbitrary row from whatever's visible, not necessarily the caller's own. In production, this manifested as one Super Admin's session resolving to a *different* Super Admin's name and email. Fixed by adding `SupabaseUserService::currentAuthUserId()` (decodes the JWT's own `sub` claim locally, no network round trip) and filtering explicitly on `auth_user_id = eq.<that>` in `PlatformAuth`, `AuthorizedDataScope::me()`, `ResolvesLandingUrl`, and this session's own new `Platform\ProfileController::index()`. Regression test: `PlatformAuthIdentityResolutionTest` fakes two visible rows with the wrong one first and asserts the caller's own is still resolved.
2. **Every "invite a new user" flow was completely broken.** `CompanyController::storeAdmin()`, `DepartmentController::storeUser()`, and `UserCreationController::store()` all read the new Supabase Auth user's id from `$invite['user']['id']` — but Supabase's real `admin/generate_link` response has `id` at the top level; there is no `user` key. Confirmed by calling the real API directly. This meant every Company Admin invite, every department user invite, and every bulk-import account creation failed with "the new account id was missing," after already silently creating a real, orphaned Supabase Auth user with no `company_users`/`department_users` link. Fixed by reading `$invite['id']`.
3. **...and even with #2 fixed, the follow-up poll used the wrong column.** All three call sites then polled `public.users` via `firstEventually('users', ['id' => 'eq.' . $newUserId, ...])` — but `$newUserId` is `auth.users.id`, which `public.users` stores as `auth_user_id`, a separate, independently-generated column from `public.users.id`. The poll always found nothing. Fixed by filtering on `auth_user_id` instead.
4. **Six tables were missing basic Postgres GRANTs for the `authenticated` role**, across four different migrations/phases: `roles`, `kpi_access_grants`, `platform_admin_assignments`, `admin_action_logs`, `kpi_templates`, `kpi_template_items`. Confirmed directly against `information_schema.role_table_grants` — every sibling table from the foundational schema has `SELECT,INSERT,UPDATE,DELETE`; these six only ever had `REFERENCES,TRIGGER,TRUNCATE`. Postgres checks table-level GRANTs *before* RLS policies run, so every one of these was completely non-functional regardless of how correct its RLS was — this is exactly why the earlier Core Platform Rule conformance check (which audits policies, not grants) never caught it. Concretely: the entire audit trail (every `logAdminAction()` write and the `AuditLogController` viewer), Platform Admin company assignment, per-KPI visibility grants, the KPI template library, and configurable department role labels had never actually worked in production. Fixed in `2026_08_17_150000_grant_authenticated_role_on_missing_tables.php` — purely additive; RLS still gates everything.
5. **KPI creation and KPI submission — the two most core, most frequently used writes in the whole Platform — failed for every non-Super-Admin caller.** `kpis_select` and `kpi_submissions_select` both route through `auth_can_view_kpi()`, which queries back into `kpis` for the row being checked. `SupabaseUserService`'s default `Prefer: return=representation` makes PostgREST implicitly re-SELECT the new row to return it, which evaluates that SELECT policy as part of the INSERT — and that failed for a Company Admin or Employee even though the INSERT's own `WITH CHECK` (`auth_can_administer_company`) independently and correctly evaluated true, confirmed via direct RPC calls, raw SQL with simulated RLS context, and repeated live inserts through PostgREST. A Super Admin never hit it (their path never needs the self-referential lookup). Fixed by adding an optional `$returnRepresentation` parameter to `SupabaseUserService::insert()` (`Prefer: return=minimal` when false — built via a parameterized `request()` rather than a second `withHeaders()` call, since chaining `withHeaders()` with a repeated key appends rather than overrides, confirmed directly) and passing `false` at the three call sites that don't use the returned row: `KpiController::store()`, `KpiController::applyTemplate()`, `KpiSubmissionController::store()`. Verified against real production with a real Employee submitting a real value end-to-end.
6. **`users_update_self`'s RLS policy had the same self-referencing-subquery recursion bug already fixed on five other tables in an earlier phase — just never applied here**, because nothing had ever run a self-UPDATE on `users` through PostgREST before: every existing "change your own account" flow goes through Supabase Auth's own `/auth/v1/user` endpoint via `SupabaseAuthService::setPassword()`, not a `users` table UPDATE. This session's own new `PlatformTelegramLinkService::generateCode()` — writing a link code to the caller's own row — is the first code ever to do that, and it failed immediately with Postgres 42P17, "infinite recursion detected in policy for relation users." Fixed the same way as the earlier five: replaced the self-referencing `WITH CHECK` subquery with a `BEFORE UPDATE` trigger (`prevent_self_role_change()`) that blocks a role change only when `NEW.auth_user_id = auth.uid()` (the caller updating their own row) — legitimate admin-driven role changes on *other* users are untouched, since for those `NEW.auth_user_id` never equals the acting admin's own `auth.uid()`.

A seventh, unrelated bug surfaced by the same real-send test: `TelegramService::webAppButton()` (pre-existing, not touched by this session before now) returned an inline-keyboard array one nesting level short of what Telegram's Bot API requires (an array of ROWS, each row an array of buttons) — every caller passed it straight through, and Telegram's own API rejected every button-bearing message ever sent with "expected an Array of InlineKeyboardButton." Never caught because nothing had ever sent a real message with a button before this session's real Telegram digest test. Fixed by adding the missing nesting level; regression test in `TelegramServiceWebAppButtonTest`.

**What's now confirmed genuinely working end-to-end against live production**, not just structurally: company creation → Company Admin invite → department/role creation → KPI creation → KPI submission by a real Employee, all as real authenticated sessions with real cookies and CSRF; company lifecycle (draft → onboarding-on-first-admin-invite → active → suspended, with the suspended company's own still-logged-in Employee getting a real 403 on their very next request); ANIRA chat replying with only that company's own real KPI data after reactivation (and correctly refusing to discuss anything while the company was suspended); and the full Telegram flow — a real link code generated by a real session, completed via the real webhook with the real secret, a real tenant-aware digest sent through the real Telegram Bot API (failing only on "chat not found," since no real Telegram account exists in this environment — an environment limit, not a code gap), and that same digest correctly skipping the linked Employee the moment their company was suspended.

### Automated tenant-isolation testing (requirement #10, 2026-08-17, same session)

User's framing: "Don't just manually test 'Andalusia can't see VFive' — create automated tests that continuously try [10 specific attacks] and expect DENIED. That turns your security architecture into something you can continuously prove." The 10 attacks: read/update/delete another company's row, change `company_id`, import another company's employee, access another company's API endpoint, access suspended company data, manipulate URL/company IDs, query through ANIRA, query through Telegram.

**Two complementary, continuously-run layers — neither one alone is the whole story:**

1. **Application layer** — new `tests/Feature/TenantIsolation/` (its own `README.md` maps all 10 attacks to specific test files and, where applicable, to the real-Postgres scenario that proves the other half). Every test plays "Company A's own admin tries to reach Company B" and proves the app refuses before any cross-tenant Supabase call is even attempted — `Http::fake()`-based, so this can only prove the APPLICATION never tries, never that Postgres RLS itself would refuse a forged request. Runs in the existing `test` job on every push.
2. **Database layer** — `database/rls-tests/tenant_isolation.sql` (written earlier this session, previously **unverified by execution** — no `psql`/disposable Postgres available on any dev machine used so far) now actually runs, for real, on every push: a new `tenant-isolation` CI job spins up a disposable `postgres:16` service container, bootstraps a minimal Supabase-compatible `auth` schema (`database/rls-tests/ci_auth_schema_bootstrap.sql` — just `auth.users` and a verbatim copy of Supabase's own `auth.uid()` function; RLS itself can't tell the difference between this and a real GoTrue-backed one, since every policy only ever calls `auth.uid()`), replays every migration in order against it, and runs the existing `php artisan platform:rls-test --dsn=...` command (built earlier this session for exactly this purpose but never actually exercised). This is the first time this suite has ever actually executed.

**No `.github/workflows` directory existed before this — there was no CI at all.** `.github/workflows/ci.yml` now runs both a `test` job (PHPUnit + `tsc --noEmit` + `npm run build`, the existing local verification loop this session has run by hand after every change) and the new `tenant-isolation` job, on every push and pull request.

**A real bug found building this, not exercised by real Postgres yet but caught in review:** `platform:rls-test`'s own safety guard refuses to run if `--dsn` is textually identical to `env('SUPABASE_DB_URL')` (its production-safety check) — but the CI job legitimately needs `SUPABASE_DB_URL` set to the disposable container for `php artisan migrate` to target it, which would trip that exact guard when passed as `--dsn` too. Fixed by using two textually-different-but-equivalent DSNs for the same disposable database (`postgresql://...` for `SUPABASE_DB_URL`, `postgres://...` — a different, equally valid libpq/Laravel scheme alias — for the value passed to `--dsn`), documented in the workflow file so a future edit doesn't "simplify" them back to matching and silently reintroduce the false refusal.

**What the new application-layer tests found and fixed, immediately:**
- `KpiSubmissionController::ensureDepartmentAccess()` calls `auth_department_ids()` via RPC unconditionally, even for a caller about to be rejected — not a security bug (it only returns the caller's own RLS-scoped department ids), but it meant this endpoint needed one more fake in tests than every other controller, which use the shared `PlatformAuthorization` trait's checks (pure in-memory comparisons, no HTTP calls at all before rejecting).
- `PlatformTelegramLinkService::completeLink()`'s test double for `/auth/v1/verify` was checking the wrong field (`token`, not the real `token_hash` the service actually posts) — caught while building a stronger two-simultaneous-user variant of the existing Telegram isolation test; both users were silently resolving to the same identity because the fake's discriminator never matched anything. A single-user-at-a-time test (the pre-existing `PlatformTelegramDigestServiceTest`) could never have caught this, since with only one identity in play there was nothing for it to collide with — directly the value of testing two tenants through the SAME code path simultaneously rather than one at a time.
- Confirmed (not a bug — a good interaction working as intended): a Company Admin's read attempt against another company's audit log correctly 403s, AND the new `platform.audit` access-denial middleware (built for requirement #8's "API activity" category) correctly writes an `access_denied` row to `admin_action_logs` for that exact attempt — an early version of the test asserted "nothing touched `admin_action_logs`" and failed on this, which was the test being wrong, not the code; fixed by scoping that assertion to reads only.

**Known limitation, stated plainly:** the `tenant-isolation` CI job itself has not yet had a real GitHub Actions run — the auth-schema bootstrap and full migration replay were reasoned through migration-by-migration (every `auth.*` reference across all migrations is exactly `auth.uid()` plus one `auth.users` foreign key, confirmed by grepping every migration file) but could not be dry-run locally: this dev environment has Docker's CLI but no running daemon, and no `psql`/local Postgres install. Treat it as unverified-by-execution, the same honest status `tenant_isolation.sql` itself carried before this pass, until it's actually gone green on a real push.

### Production-grade tenant isolation, executed for real (2026-08-18, new session)

User's framing: tenant isolation must become "a provable, continuously enforced production guarantee, not merely an architectural assumption" — explicitly not satisfied by CI configuration existing on paper. `tenant_isolation.sql` had been written since Phase 3 but never actually run (no `psql`/disposable Postgres available on any dev machine used so far, confirmed and re-confirmed across multiple sessions). This session had a working Docker daemon for the first time (previously only the Docker CLI was present, not a running daemon) — that changed what was actually possible, and it was used to run the real thing rather than continue documenting the gap.

**Real execution achieved.** A disposable `postgres:16` container (`docker run`, port 55432) was bootstrapped with `ci_auth_schema_bootstrap.sql`, all 24 migrations were run against it via `SUPABASE_DB_URL` pointed at the container, and `php artisan platform:rls-test` (a real `psql` client, installed via `scoop install postgresql` since none existed locally either) ran `tenant_isolation.sql` against it for real — the first time in this project's history. This immediately surfaced three real bugs that no amount of static reading had caught:

1. **A duplicate `sessions` table migration.** `2026_06_19_033957_create_sessions_table.php` re-created a table `0001_01_01_000000_create_users_table.php` (Laravel 11's stock skeleton) already creates — invisible on any dev machine whose sqlite file predates the second migration, but fatal on any genuinely fresh database, including this project's own CI job (which uses `DB_DATABASE=':memory:'` and had never actually been run). Fixed by guarding the redundant migration's `up()` with `Schema::hasTable('sessions')` rather than deleting it, preserving migration-tracking history on any environment where it's already recorded as applied.
2. **The CI auth-schema stub was missing Postgres role/grant setup a real Supabase project provides for free.** `ci_auth_schema_bootstrap.sql` only ever stubbed `auth.users`/`auth.uid()`; it never created the `anon`/`authenticated`/`service_role` Postgres roles themselves, nor the baseline table-level GRANTs Supabase's own project template silently applies to every table (separate from `2026_08_17_150000`'s explicit grants, which only cover the six tables that were *missing* what Supabase had already applied to everything else — see the "six tables were missing basic Postgres GRANTs" finding above). Fixed with role creation added to `ci_auth_schema_bootstrap.sql` and a new `database/rls-tests/ci_post_migration_grants.sql`, run after `migrate` and before the RLS suite, replicating exactly what Supabase already does in production (this doesn't weaken what's tested — Postgres checks table GRANTs before RLS, so this only clears the precondition for RLS to be the actual gate).
3. **A real, previously undiscovered security gap: `auth_department_ids()` never checked individual `company_users.status`.** `auth_company_ids()`/`auth_role_in_company()` have checked `cu.status = 'active'` since Phase 5; `auth_department_ids()` only ever excluded a suspended/archived *company*, never a suspended *individual membership*. Every policy that ORs in `department_id in (select auth_department_ids())` inherited that gap — `department_users_select`, `kpi_access_grants_select`, `reports_select`/`insert`, and (via `auth_can_view_kpi()`'s department-grant branch) `kpis_select` and `kpi_submissions_insert`. Concretely: a suspended Employee whose department had an explicit `kpi_access_grants.department_id` grant kept read (and submission-insert) access to that KPI after being suspended — exactly the "suspended user retains operational access" failure this whole phase exists to close, just via a path scenario 7/8/9 never exercised (they suspend the whole *company*, never a lone member of an otherwise-active one). Empirically confirmed against the live container both before the fix (a suspended test user could see a coworker's `department_users` row and a department-granted KPI) and after (0 rows, both cases; a fresh coworker-visibility check specifically isolated this from the unrelated "you can always see your own membership row" branch, which is correct behavior and not part of the bug). Fixed once, in the shared helper every affected policy already calls, via `2026_08_18_000000_fix_auth_department_ids_suspension_bypass.php` — **written and verified against the disposable container in this session; not yet applied to production**, since an RLS-function change is exactly the kind of production action that needs explicit sign-off, not a silent push.

**The suite grew from 9 scenarios to 13**, adding the specific attack classes requested: cross-tenant row movement (scenario 7 — attempts to `UPDATE company_id` on Company A's own KPI, asserting the immutability trigger's exact error message, not just an RLS no-op, since after scenario 11 suspends the company an RLS-side no-op and a trigger rejection would look identical), a direct cross-tenant INSERT (scenario 8 — a Company A admin inserting a brand-new `kpis` row with `company_id` set straight to Company B, distinct from the existing forged-`company_id`-on-`kpi_submissions` scenario which exercises the derive-from-parent-department path instead), role self-escalation (scenario 9 — a Company Admin attempting to set their own `users.role` to `richworks_super_admin`, asserting `prevent_self_role_change()`'s specific error), and the individual-suspension-bypass fix above (scenario 10). All 13 scenarios — including the pre-existing 6 — now have real, confirmed pass/fail status for the first time, not just "written and presumed correct." Scenario 6 (no DELETE policy on `kpis`) also had its own detection bug fixed en route: a missing RLS policy for a command doesn't raise `insufficient_privilege`, it silently matches zero rows (the same as an UPDATE with no matching policy) — the original code only caught exceptions and treated "none thrown" as "delete succeeded," which running it for real immediately proved wrong. Now checks `row_count`, the same way the adjacent UPDATE scenario already did.

**CI updated** (`.github/workflows/ci.yml`) to run the new `ci_post_migration_grants.sql` step between `migrate` and `platform:rls-test` — without it, the `tenant-isolation` job would have failed on its very first real run with "role authenticated does not exist" / "permission denied for table companies," the exact errors hit locally before the fix. **Still not yet confirmed on a real GitHub Actions run** — reasoned through and now locally verified end-to-end against an equivalent disposable Postgres, but the actual CI job itself has never executed; that gap is now purely "has anyone pushed and watched it," not "does the logic work."

**Deployment-blocking (requirement #2) is partially satisfied and partially a pending action, stated honestly rather than glossed over.** The CI job exists, runs the real suite, and fails loudly on a genuine RLS regression (confirmed by the FAIL-marker parsing in `platform:rls-test`). What's still missing: this repository has no GitHub branch-protection rule requiring the `tenant-isolation` (or `test`) check to pass before merging to `main`, and deployment is via Railway (`railway.toml`), which deploys directly from `main` with no GitHub Actions "deploy" job of its own to gate. Making CI *actually* block deployment therefore means adding a required-status-check branch protection rule on `main` — a repository governance setting, not a code change, and one this session had no `gh` CLI or GitHub token available to make. Needs a repo admin to configure via GitHub's own branch protection settings (Settings → Branches → add rule on `main` → require status checks `test` and `tenant-isolation`).

**Privileged-path audit (requirement #4).** A full sweep (not a re-read of prior claims) confirmed `SupabaseService::TENANT_OWNED_TABLES` is complete and accurate against the current schema — its 13 guarded tables plus the 5 documented exemptions together equal exactly the 18 tables the migrations actually create; nothing is missing from the guard. Roughly 40 files inject `SupabaseService`; all either touch exempt tables (the same narrow set already documented), get refused by the guard, or target tables that don't exist in production at all (`employees`, `user_company_roles`, `telegram_project_tasks`, etc.) — a large surface whose only safety net is the guard throwing, worth keeping in mind as fragile-by-construction rather than actively unsafe. `grep -rn "DB::connection|DB::select|DB::statement|DB::table" app/` returns zero matches — every raw-SQL/direct-connection use is confined to `database/migrations/*.php`. Import scripts (`ImportController`/`ExcelImportService`) derive `company_id` strictly from the route parameter throughout, never from uploaded file content, for departments, KPIs, and staged employees alike. Every token-minting/impersonation path (`AuthorizedDataScope`, `TelegramAuthorizedScope`, `PlatformTelegramLinkService`) requires a real caller token or mints a genuine Supabase session — none can be constructed from a bare user ID.

**One real, live finding from that audit, fixed in this pass: `TelegramDigestService::broadcast()` (the legacy morning/evening reminder, `App\Jobs\Send{Morning,Evening}TelegramDigest`, reachable via `POST /telegram/cron/morning|evening` guarded only by a shared secret with no tenant dimension) was reasoned about as dead code in earlier sessions on the correct logic at the time — but that reasoning predates `2026_08_17_140000_add_telegram_linking_to_platform_users.php`, which added `telegram_chat_id` to the exact same `users` table this broadcast queries (via the exempt-from-the-guard `users` table, so nothing blocked it). The moment any real Platform user links Telegram through `/platform/profile`, this legacy path became live again and unsafe: it queried `users` for anyone with a non-null `telegram_chat_id` and messaged all of them with zero company or suspension scoping — a suspended user, or a member of a suspended company, kept receiving these reminders indefinitely. `PlatformTelegramDigestService` (via `TelegramAuthorizedScope`, `/platform/telegram/cron/*`) already replaces this correctly against the identical column. Retired `TelegramDigestService::broadcast()` to a logged no-op rather than deleting the class (the routes/commands/jobs that call it stay resolvable), with a regression test (`TelegramDigestServiceRetiredTest`) asserting it never queries Supabase or sends a Telegram message. This is a genuine behavior change to a previously-live production code path, not just a documentation update — flagged explicitly for that reason.**

**Isolation test report:** a structured summary (test counts, tables/roles/scenarios covered, known exceptions, remaining risks) was produced covering all of the above — see the artifact linked in the closing summary of this work, or regenerate from this section plus the `tenant_isolation.sql`/TenantIsolation PHPUnit suite for the current numbers.
